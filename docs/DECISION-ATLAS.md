# Workflow Editor Decision Atlas

This is the repository-owned, feature-oriented source of **owner-approved product intent** for Workflow Editor. Decisions describe what the product should do, not a claim that current code implements or verifies it. This Atlas begins with the owner's free-flow steering on 2026-10-14; existing `README.md`, `CONTEXT.md`, ADRs, and `docs/roadmap.md` remain useful descriptions of current APIs, architecture, and implementation sequencing. In particular, the current hand-written TypeScript-like type resolver is **not** evidence that the intended native-TypeScript direction below has shipped.

## Editing rules

- **Decision** and **Question** are the only semantic leaf kinds; headings group product capabilities.
- Keep IDs stable. Append new entries; never silently renumber, overwrite, or remove historical decisions.
- Retain an answered Question and append a new Decision marked `Answers <ID>`. Record revisions with a new `Supersedes <ID>` Decision.
- An unresolved Question is not automatically an implementation blocker. GitHub issues track bounded work, not a second authority for product intent.
- Implementation belongs in Workflow Editor for editing, graph validation, and compilation; execution/transport mechanics belong to the separate workflow engine and runner. Generic graph interaction belongs to graph-editor.

## 1. Typed ports and data

- **1.1 Use the real TypeScript type system for workflow typing.**  
  Status: adopted 2026-10-14.  
  Input and output ports have TypeScript types. TypeScript's own type checker is authoritative for type compatibility; do not maintain a second, independently approximated assignability/type language. Types and reusable declarations should be usable in browser-based authoring and supported hosts. Static compatibility does not itself validate actual runtime values, because TypeScript types are erased at runtime.

- **1.2 Expose type propagation and possible outputs before execution.**  
  Status: adopted 2026-10-14.  
  Connecting nodes and choosing conditional branches should let users inspect which types can flow into inputs, out of individual ports, and out of the finished workflow. Incompatible connections receive actionable diagnostics rather than silently changing types. Show possible branch output types; do not claim to know runtime branch choices or computed values in advance.

- **1.3 Support JSON-compatible and annotated binary values.**  
  Status: adopted 2026-10-14.  
  Workflow ports can describe structured JSON-compatible values and binary data, including audio such as WAV. Users can see the declared TypeScript type and meaningful binary format/medium annotations. Binary values should not have to be converted into JSON arrays of bytes solely to pass between nodes. The editor describes these contracts; engine/runner data transport is a separate responsibility. Streaming semantics remain open in 1.4.

- **1.4** [question] **How should binary values move between executing nodes?**  
  Resolved 2026-10-14 by 1.5.  
  Should version one carry complete binary values or references to them (A), support incremental streamed chunks with backpressure (B), or expose both buffered and streamed port modes (C)? The engine currently restricts persisted run inputs/results to JSON-safe values, so annotations alone cannot implement end-to-end binary execution.

- **1.5 Support both buffered and streamed binary ports.**  
  Status: adopted 2026-10-14. Answers 1.4 (option C).  
  Nodes can declare **buffered** binary inputs/outputs for a complete payload (or a reference to it), and **streamed** binary inputs/outputs for incremental chunks. The port contracts visibly distinguish these modes alongside their TypeScript types and binary-format annotations (1.1, 1.3). Connections must respect both type compatibility and payload mode; converting between modes is explicit, not silent eager buffering or implicit stream consumption. Streaming execution supports bounded flow/backpressure rather than unbounded accumulation. The editor exposes and compiles these contracts; `workflow-runner` owns per-run chunk propagation and flow control, while `workflow-engine` owns dispatch/run-state and persistence boundaries. Engine run records must not start storing raw binary or live streams inside the existing JSON-safe state model. The user should be able to author and inspect either mode without needing an execution engine embedded in the editor.

- **1.6** [question] **How should one streamed output feed multiple consumers?**  
  Resolved 2026-10-14 by 1.7.  
  When a streaming output is connected to two or more downstream nodes, should users explicitly insert a fan-out/tee node that exposes the extra streams (A), or should ordinary multiple connections automatically broadcast the chunks with bounded backpressure for slow consumers (B)? Either way, do not silently turn an unbounded stream into a buffered value. This affects streamed DAG branching and the runner's flow-control contract.

- **1.7 Automatically fan out one output to multiple consumers.**  
  Status: adopted 2026-10-14. Answers 1.6 (option B).  
  One node output may connect directly to multiple compatible input ports on downstream nodes, like using the same variable or value in several expressions. **No explicit Tee/fan-out node is required.** A buffered value is produced once and made available to each connected downstream consumer; adding a connection does not independently re-execute the producing node. For streamed binary outputs, the runner automatically broadcasts the incremental chunks to each active downstream consumer with bounded backpressure and without silently discarding chunks, implicitly converting the stream to a whole buffered payload, or requiring a separate duplication node. Stream sharing must work with ordinary DAG branches and cancellations without unlimited memory growth. This is **one-output-to-many-input fan-out**, not a decision that unrelated outputs may automatically converge onto the _same input port_; that behavior remains governed by that input's explicitly declared cardinality and type. The editor owns connection authoring and serialized contracts; the runner owns actual value propagation, stream distribution, and resource lifecycle.

- **1.8** [question] **How should multiple sources connect to one input port?**  
  Answered 2026-10-14 by Decision 1.9 (option A); retained for historical traceability.  
  When two node outputs are connected to a single downstream input, should the receiving node explicitly declare whether its input accepts one value or a collection of values (A, matching the current cardinality contract), or should adding a second connection automatically turn an ordinary input into a multi-value collection (B)? This is distinct from approved automatic one-output-to-many-consumer fan-out (1.7). The answer determines whether an input's TypeScript type remains fixed by its node definition or changes based on how many edges are connected.

- **1.9 Require explicit input cardinality and preserve declared types.**  
  Status: owner-approved 2026-10-14. Answers 1.8 (option A).  
  A Node's input Port declares whether it accepts one incoming Connection or multiple incoming Connections, and the TypeScript Port Type remains defined by that Node rather than changing with the number of connected sources. Ordinary single-value inputs accept at most one incoming Connection; adding a second must be rejected with an actionable cardinality diagnostic, not automatically transform the input into an array or collection. A deliberate multi-source input explicitly declares its multi-connection cardinality and its intended collection-valued type; compatible sources may connect within those declared bounds. Connecting or disconnecting sources must not silently rewrite the input's declared type. Preserve the existing default single-input behavior and the separately defined expandable JSON constructor behavior; use the existing Workflow Editor cardinality contract rather than a competing system. Automatic **output fan-out** remains approved by 1.7 and is separate from **input fan-in**. Editor validation, composing, serialization, and compilation preserve declared cardinality and type information; the editor does not own runtime collection assembly, stream scheduling, or delivery. This is approved intent, not a claim that all editing paths and consumer acceptance tests have passed.

## 2. Workflow graph and composition

- **2.1 Use directed acyclic graphs for the initial execution-ready workflow model.**  
  Status: adopted 2026-10-14.  
  Workflows use directed connections without cycles, supporting predictable ordering, static analysis, and final output-type inspection. Provide basic control-flow nodes, including conditional branches and joins. Structural acyclicity does not guarantee that an arbitrary asynchronous node terminates; recursion through referenced documents remains an open policy question (2.5).

- **2.2 Group, ungroup, collapse, and expand nodes directly on the canvas.**  
  Status: adopted 2026-10-14.  
  Users can organize nodes into groups, undo those groupings, and minimize or expand ordinary nodes without losing their connections or making the workflow difficult to navigate. These are normal editing actions, not special execution operators.

- **2.3 Turn a selection of nodes into a composed node.**  
  Status: adopted 2026-10-14.  
  Selected nodes can become one node whose externally visible inputs and outputs correspond to the selected subgraph's boundary. Users can recover the constituent nodes by decomposing the composition. Whether compositions should also become reusable catalog templates is not yet specified (2.4).

- **2.4** [question] **Should a composed group become a reusable node template?**  
  Answered 2026-10-14 by Decision 2.9 (option B, with an explicit detach-to-copy action); retained for historical traceability.  
  Is composition a local wrapper in one workflow (A), a published reusable node across workflows (B), or both, with an explicit choice when composing (C)? This affects catalog identity, versioning, and updates to existing instances.

- **2.9 Publish linked reusable compositions and allow detaching a local copy.**  
  Status: owner-approved 2026-10-14. Answers 2.4 (option B, with explicit detachment).  
  Users may publish a selected, composed subgraph as a **reusable Node Template** in the existing Editor Catalog and insert **linked instances** of that shared definition into multiple Workflow Documents. Linked instances retain the shared definition's identity; changes to the published definition propagate to linked instances rather than silently creating independent copies each time it is used. A user who wants to change one instance independently can explicitly **detach / unlink** it, materializing the currently referenced definition as a local, editable composed-node copy in that Workflow Document. The detached copy keeps its compatible boundary ports/connections and no longer receives future shared-template updates; detaching it neither edits the source definition nor changes other linked instances. Ordinary grouping/local composition from Decision 2.3 remains available and is not silently published or linked. Distinguish linked reuse from an embedded copy in the canvas and inspector, preserve source identity or detached content across save/export/reopen and compilation, and reuse existing Node Template, composition and Workflow Reference foundations rather than creating a second template/graph system. The editor owns authoring, source resolution, compatibility diagnostics and compilation; the runner does not manage template publication or dynamic editor-catalog updates. Handling edits that would break linked instance ports/types remains Question 2.10. This is approved direction, not proof of an implemented linked-template experience.

- **2.10** [question] **What happens when a shared template update breaks existing linked connections?**  
  Answered 2026-10-14 by Decision 2.11 (option B); retained for historical traceability.  
  When an edit to a published shared template changes or removes inputs, outputs or TypeScript contracts required by existing linked instances, should the editor **reject publication until those consumers are reconciled** (A), or **allow a new revision but keep affected instances on their last compatible revision until explicitly upgraded** (B)? Both should expose the incompatibility and preserve the explicit detach-to-copy action; routine compatible edits continue to reach linked instances under Decision 2.9. Do not silently break a consuming workflow or claim an incompatible revision was accepted.

- **2.11 Version incompatible shared-template changes and protect existing linked instances.**  
  Status: owner-approved 2026-10-14. Answers 2.10 (option B).  
  Publishing a shared Node Template change that would break an existing linked instance's declared boundary ports, connections or TypeScript types creates a **new immutable published revision** instead of rejecting the update or silently rewriting the consuming Workflow Document. An affected linked instance **retains its last compatible revision**, remains usable with the same validated connections and visible revision identity, and **upgrades to the incompatible revision only through an explicit user action** with clear compatibility diagnostics. Compatible template updates continue to propagate automatically to linked instances under Decision 2.9; unaffected instances need not be held back merely because another consumer cannot accept an update. A linked instance must never silently switch to an incompatible revision, lose its connected ports, or rebind to a different source by name alone. The existing **Detach / Unlink** action materializes the selected instance's currently resolved revision as a local editable copy, without changing shared history or other instances. Preserve revision identities, explicit upgrade state and compatible source resolution through save/reopen, export/import and deterministic compilation; a compiled workflow must resolve an immutable definition, not depend on a live catalog edit during execution. Editor and registry own version selection, inspection, compatibility checks and user-controlled upgrades; runtime scheduling/execution remains outside this repository. This decision does not assert that linked-template publishing or revision migration has already been implemented.

- **2.5** [question] **Does the initial acyclic rule also prohibit recursive workflow references?**  
  Answered 2026-10-14 by Decision 2.6 (option C); retained for historical traceability.  
  Should all referenced workflows form one acyclic call graph (A), should each document alone be acyclic while references may recur (B), or should recursive references be allowed only with explicit bounded recursion (C)? Existing reference navigation can be recursive even though ordinary graph edges are acyclic.

- **2.6 Allow bounded recursive workflows and iterative approximation.**  
  Status: owner-approved 2026-10-14. Answers 2.5 (option C).  
  Workflow Documents may intentionally **re-enter a referenced workflow or repeat a calculation** to improve an approximation, with optional early exit when a declared stopping/convergence condition is met. **Every recursive or iterative path must have a finite, explicit bound** (such as maximum iterations or invocation depth), validated before execution and enforced by the runner even when its stopping condition never becomes true; execution also remains subject to cancellation and finite time limits so a non-returning operation cannot evade the overall bound. An unbounded reference cycle or repeat is not an executable workflow. An enforced stop does **not** prove the algorithm converged or met its desired accuracy; results and diagnostics must distinguish normal convergence from a limit being reached. Preserve Decision 2.1's acyclic **ordinary node connections within each workflow body**; repeated execution and feedback are explicitly scoped control-flow/recursive-reference constructs, not unrestricted arbitrary cyclic graph edges. Preserve typed input/output contracts at iteration boundaries. The editor authors and validates bounded loops/references and compiles their contracts; the runner owns actual iteration, guard enforcement, timeouts and cancellation; the engine retains registration/dispatch/run-state ownership. Evolve the shared compiled contract explicitly and maintain old-version conformance rather than silently interpreting new recursion using compiled-v1 DAG semantics. The behavior of an available best-so-far approximation when a limit is reached remains open (Question 2.7).

- **2.7** [question] **What result should a bounded iterative workflow expose when its limit is reached before convergence?**  
  Answered 2026-10-14 by Decision 2.8 (option A); retained for historical traceability.  
  If a calculation has produced a candidate approximation but has not met its stopping criterion by the enforced limit, should it return that candidate as a clearly marked **partial/non-converged** output (A), or stop with an explicit **limit-exhausted** failure without a normal output (B)? Both must terminate within configured bounds; neither may claim the requested precision was reached. This choice does not affect successful early convergence or cancellation before any candidate exists.

- **2.8 Return a clearly marked best-available approximation at the iteration limit.**  
  Status: owner-approved 2026-10-14. Answers 2.7 (option A).  
  When an explicitly bounded recursive or iterative workflow reaches its invocation/iteration limit without satisfying the declared stopping or convergence condition, **return the best available valid candidate if one exists**, clearly marked **partial / non-converged** rather than reported as ordinary converged success. Preserve the stopping reason (limit exhausted), actual iteration count, configured bound, and only convergence/quality measurements the workflow genuinely computed. The workflow's own candidate-selection or evaluation contract determines which candidate is best; do not invent a quality metric or silently equate the most recent candidate with the best. Downstream consumers must be able to distinguish and intentionally handle the non-converged result through the typed output/status contract, without being told the requested accuracy was achieved. If no candidate exists, report the absence of a usable result rather than manufacturing one; cancellation, timeout and executor failure retain distinct outcomes and are not automatically converted into partial success. The editor authors, displays and compiles the result/status contract; the runner enforces bounds and returns the labeled candidate with execution provenance; the engine retains run-state and JSON-safe persistence authority. Keep existing compiled-v1 DAG behavior unchanged and version any new contract deliberately. This records intended behavior, not completed implementation.

## 3. Type-visible editing

- **3.1 Make port types recognizable by consistent, configurable colors.**  
  Status: adopted 2026-10-14.  
  Each displayed type has a consistent color across the workflow, and users can set or override its color. Matching colors help with visual scanning of inputs and outputs, while visible type labels and actual compatibility diagnostics remain authoritative: assignable TypeScript types are not necessarily identical, and color alone must not determine connection validity.

## 4. Release maturity and feature delivery

- **4.1** [question] **Should Workflow Editor target a stable 1.0 release now?**  
  Answered 2026-10-15 by Decision 4.2 (option B); retained as the historical Question.  
  Choose A: complete 1.0 stability and platform guarantees before expanding features; B: keep version 0.x, deliver usable authoring features, and revisit 1.0 when consumers justify it; or C: stabilize a minimal 1.0 core while advanced features remain experimental. This decides the release priority, not permission to break working consumers.

- **4.2 Keep Workflow Editor feature-first on 0.x and defer 1.0.**  
  Status: owner-approved 2026-10-15. Answers 4.1 (option B).  
  Continue an explicitly pre-1.0 package and prioritize independently verifiable editing and composition in the real Pages workbench, including typed/binary ports, bounded workflows, and versioned linked templates (1.x–3.x; issues #61, #64 and #65). Preserve delivered capabilities from #59 and #60. The formal 1.0 release-readiness program in #13 (W-01) is deferred. The remaining W-02–W-12 issues are feature and quality work to pursue when they enable a real user-facing slice, not a mandatory sequence or collective 1.0 gate.
  Do not require arbitrary stability freezes, fixed React/browser/Node/bundler support matrices, deprecation windows, numeric workload budgets, or a release date before current feature delivery. Preserve existing consumer interfaces or provide explicit migrations; retain correctness, data recovery, accessibility and appropriate testing. Graph gestures remain owned by graph-editor, typed design and compilation by workflow-editor, and execution by workflow-engine/workflow-runner.
  Revisit possible 1.0 promotion only when concrete consumer integrations and verified workflows establish which interfaces, workloads and compatibility obligations need guarantees. Seek owner approval then, rather than inventing numeric targets or support promises now. This is product intent, not a claim that feature acceptance or a stable release has occurred. ([Owner choice B, 2026-10-15](https://github.com/moritzbrantner/workflow-editor/issues/13))

## 5. Practical reference workflows

- **5.1 Maintain data pipelines and AI/media workflows as independent first-class examples.**  
  Status: owner-approved 2026-10-16, choice C (basic-functionality steering).  
  The Pages workbench should provide two independently usable, directly loadable example families: **(1) a conventional data pipeline**, demonstrating source → transform → validate → conditionally branch → output; and **(2) an AI/media workflow**, demonstrating a media input → a host-provided external model/media operation → output processing → saved artifact/reference. Both demonstrate the same generic typed workflow authoring, inspection, save/reload and compilation facilities, without treating either as the canonical architecture for the other. Keep examples grounded in real visible interaction rather than adding another orchestration framework. ComfyUI remains authoritative for its own media-generation graph and inference; in a generic workflow, invoke one ComfyUI workflow as one external, versioned executor operation through the existing asset-tooling boundary. Static Pages demonstrations must not claim to execute an unavailable runtime or require credentials or network access merely to open and edit examples; real execution acceptance belongs to a connected host/runner. This does not remove other documented reference-application ideas from issue #22, nor impose a priority ordering between these two families.

- **5.2 Open directly into an editable example workflow.**  
  Status: owner-approved 2026-10-16, choice A (initial experience).  
  On first opening the Pages Workflow Editor, show a real, immediately editable example Workflow Document directly on the canvas, rather than a blocking template chooser or empty initial canvas. The user can select, modify, inspect, save and compile it through the normal editor functionality. Keep the other example family from Decision 5.1 and the ability to start a blank document readily discoverable without an introductory screen. Honor an explicitly selected or previously saved user document instead of overwriting it with the initial example; the example is a starting document, not a substitute for saved work. Do not add a marketing hero or a duplicate tutorial UI. This decision does not select which of the two approved example families is the initial default.

- **5.4 Default first-time visitors to the editable data pipeline example.**  
  Status: owner-approved 2026-10-17, choice A (answers initial-example selection Question 5.3).  
  For a first-time user without an explicitly selected or existing saved document, Workflow Editor opens the **data pipeline** example from Decision 5.1 directly in the editable canvas: source → transform → validate → conditional branch → output. Do not open an AI/media example or a chooser as the initial screen. The AI/media example and a blank Workflow Document remain readily accessible. Preserve the existing saved/selected document across reload; never replace it with the default example. Keep the example fully inspectable, editable, savable and compilable without requiring an external service.

- **5.5 Offer both a searchable Node Template palette and contextual node creation.**  
  Status: owner-approved 2026-10-17, choice C (node-creation experience).  
  Users can browse/search a categorized Node Template palette and add a Node by clicking or dragging a template. Users can also create Nodes directly from an empty canvas context action or from a Connection/Port context action, with applicable TypeScript-compatible templates filtered or highlighted. Both entry points use the **same authoritative Editor Catalog/Node Template registry and node-creation command**, not separate template definitions or duplicated creation logic. The canvas remains primary; palette and menus are discoverable without permanently obstructing it. Preserve keyboard/touch-accessible alternatives and existing validation/undo behavior. Generic graph gesture/menu positioning belongs to graph-editor; workflow-specific type compatibility and template choice belong to Workflow Editor. This is intended behavior, not implementation evidence.

- **5.6 Edit frequent node settings inline and advanced settings in the inspector.**  
  Status: owner-approved 2026-10-17, choice A (node editing experience).  
  Selecting a Node exposes its detailed settings in the inspector, while its frequent, task-relevant controls remain directly editable on the canvas. Typical inline edits include common scalar values, dynamic object/array property names and rows, and contextual node actions; uncommon configuration, precise numeric/position controls, and secondary metadata belong in the inspector. Do not maintain two competing primary editors for the same field or clutter idle nodes with decorative fields. Both surfaces commit through the same workflow document mutation/validation/undo authority. Keep direct editing accessible by keyboard and touch; preserve text/numeric drafts, exact values, connections, focus and graph gestures. Reuse graph-editor's public node composition and chrome, without portals or private DOM-selector overrides. The exact field split may be established from actual usage and existing node families rather than another sequence of owner questions. This is product direction, not implementation evidence.

- **5.7 Support both connected Run actions and separate execution through one compiled contract.**  
  Status: owner-approved 2026-10-17, choice C (workflow execution experience).  
  A user can start and observe an execution directly from the Workflow Editor when a suitable runner is connected, or export/compile the same Workflow Document for execution by a separate runner/host. Both paths use the same versioned, execution-neutral compiled workflow contract; Workflow Editor must not add an independent execution engine or duplicate scheduling, retries, transport and resource lifecycle. A connected Run action offers useful canvas node progress, errors and result inspection from runner-supplied events/snapshots, leaving the authored Workflow Document, undo history and dirty state unchanged. The Pages editor without a connected runtime continues to support authoring, validation and compilation without pretending to execute or requiring external credentials. Runtime host integration remains explicit; Workflow Runner owns one-run execution and Workflow Engine owns durable orchestration. This is product intent, not evidence of an implemented connected Run experience.

- **5.8 Inspect both node results and complete run history from one authoritative evidence source.**  
  Status: owner-approved 2026-10-17, choice C (execution results experience).  
  After executing a Workflow Document through a connected runner, users can select a Node to inspect its run-specific inputs, outputs, errors, status and timing directly from the graph. They can also open a run-history/timeline view to compare and navigate previous executions and drill into their node results. Both views derive from the **same runner/host-owned execution records**, not independent state stores or duplicated result calculations. Run history is available when a connected host provides retained run evidence; a standalone static Pages editor must not fabricate historical executions or persist runtime state in design documents. Keep the canvas primary for ordinary editing and expose history on demand. Workflow Editor owns only presentation and selection of host-supplied evidence; Workflow Runner owns execution events and Workflow Engine/host owns durable run history. This does not approve a second runner or a new editor-owned history backend and does not claim implementation.

- **5.9 Support both portable workflow bundles and a shared versioned workflow library.**  
  Status: owner-approved 2026-10-17, choice C (workflow reuse experience).  
  Users can export a Workflow Document together with its required referenced-document dependency closure as a portable bundle, import it into another library/application, and maintain an **independent editable copy**. They can also publish versioned workflow definitions into a shared library for other applications to reference by stable identity and immutable published version. Both modes use the same canonical Workflow Document and compiler contracts, without separate authoring systems. Bundle import must preserve references and avoid overwriting existing documents without an explicit choice. Published shared references resolve through an authoritative library/registry; they must not silently drift to incompatible versions or mutate already-published definitions. Reuse existing Workflow Library, bundle planning (#21), versioning and Node Template registry boundaries where applicable; do not introduce a second registry solely for this feature. This authorizes the user-facing reuse modes, not a cloud marketplace, authentication provider, hosting service, or new runtime deployment protocol. No implementation is claimed.

- **5.10 Retain automatic document version history with manual named milestones.**  
  Status: owner-approved 2026-10-17, choice B (workflow version management).  
  Workflow Documents retain recoverable automatic revisions as meaningful edits are saved, and users may mark important states as named milestones. Users can inspect/compare revisions and explicitly restore a chosen version without silently overwriting other saved history. Preserve a clear distinction among transient undo/redo, automatically retained document history, user-named Saved Versions, and immutable published shared-library revisions from Decision 5.9. Reuse the existing Workflow Library/version storage and semantic diff capabilities; do not introduce Git-style branching or merge operations as a prerequisite. Automatic history must not record runtime execution overlays, generate redundant identical revisions, or require users to name every save. Recovery and retention specifics can follow existing repository contracts and practical acceptance rather than further owner-level exception questions. This is approved intent, not evidence of implementation.

- **5.11 Support manual, scheduled and event-triggered workflow execution.**  
  Status: owner-approved 2026-10-17, choice B (workflow automation).  
  A workflow may be started manually, on a configured schedule, or in response to an external event such as a webhook, file arrival or repository event. Workflow Editor exposes the appropriate trigger configuration and its association with the same versioned compiled Workflow Document, but does not implement a scheduler, webhook listener, event ingestion service or a second execution runtime. Workflow Engine/host owns trigger registration, scheduling, delivery, permissions and durable orchestration; Workflow Runner executes one dispatched run. Workflows can still be authored, validated and compiled in static Pages without an attached host, where live trigger activation is unavailable. Reuse existing engine/host integration contracts; implementation details and routine operational exceptions do not require further owner-level steering. This is user-facing intent, not evidence that scheduled/event-triggered execution exists.

- **5.12 Provide typed workflow parameters and named reusable input profiles.**  
  Status: owner-approved 2026-10-17, choice B (workflow inputs).  
  Workflow Documents declare typed input parameters, defaults and required values. The editor generates a manual-run input form from those declarations and lets users save, name, select and edit reusable sets of values as **input profiles** for repeated runs and for compatible scheduled/event trigger configurations. Profiles are distinct from workflow definitions and immutable published revisions; changing a profile does not silently mutate a compiled workflow or an earlier run's recorded inputs. The existing TypeScript Port Type/compiler contract remains authoritative for compatibility. Runtime hosts/Workflow Engine own binding trigger/event data, credentials and dispatch; Workflow Runner receives validated inputs for one run. Do not store secrets as ordinary profile values or add a second type checker, parameter language or scheduler. Static Pages can edit profiles without claiming an unavailable run happened. This decision establishes product functionality, not implementation evidence.

- **5.13 Inspect failed Nodes and selectively rerun from a chosen Node using valid prior results.**  
  Status: owner-approved 2026-10-17, choice B (workflow debugging experience).  
  Users can inspect a failed Node's inputs, outputs, errors and execution context, fix the cause, and request a new execution from a selected Node onward, reusing valid compatible upstream results rather than automatically restarting every preceding Node. Reuse is permitted only where prior result provenance and the selected workflow definition/input identities establish compatibility; never silently reuse stale outputs or repeat external side effects merely to reconstruct a view. If reuse is not valid or unavailable, show why instead of claiming the partial rerun succeeded. The editor owns node selection, result inspection and the action to request a partial rerun; Workflow Runner/host owns replay planning, cache/result validity, attempts and side effects, while Workflow Engine/host owns retained evidence. The ordinary full Run capability from 5.7 remains available; the approved debugging fast path is selective replay. Do not build a second executor or editor-owned results store. This records intent, not implementation.
